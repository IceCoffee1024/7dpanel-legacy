# 六阶段简化路线图

## 执行原则

本路线图把[简化工作章程](README.md)转化为顺序明确、可停止、可回滚的工作。复杂度候选及其证据由[复杂度盘点](inventory.md)记录。

路线图遵循以下规则：

- 不推倒重写；
- 不同时开展大范围功能扩张和架构收缩；
- 不先设定必须合并哪些工程或删除多少接口；
- 先完成基线和追踪样本，再批准结构变化；
- 每一阶段必须满足退出条件，不能用计划或局部代码替代证据；
- 当前实现、测试和发布状态仍只由[系统架构](../architecture.md)与[测试策略](../test.md)拥有；
- 产品、导航、架构或测试合同发生变化时，必须更新相应权威文档。

## 总体状态

| 阶段 | 名称 | 状态 | 主要产物 |
|---|---|---|---|
| 1 | 停止扩张并建立基线 | 已完成 | 冻结规则、当前验证基线、核心优先级 |
| 2 | 复杂度盘点 | 已完成 | 三个追踪样本、已确认候选 |
| 3 | 删除偶然复杂性 | 已完成 | 小批量、可回滚简化 |
| 4 | 收敛为三条标准路径 | 已完成 | 查询、普通修改、危险异步操作 Golden Path |
| 5 | 自动化机械工作 | 已完成 | 生成器、检查器和可复现模板 |
| 6 | 建立持续认知预算 | 已完成 | 可执行的局部理解与变更成本门禁 |

本表只表示简化计划进度，不表示任何 `CAP-##`、`NFR-##` 或旅程已经验证。

# 阶段一：停止扩张并建立基线

## 目标

在继续修改结构前，确认当前代码、测试、契约和发布边界的真实状态，并阻止新的偶然复杂性继续进入系统。

## 已生效约束

本阶段开始后：

- 不新增没有同一变更中生产消费者的接口、Registry 或未来基础设施；
- 不新增通用插件、消息总线、状态机、Repository 或生命周期框架；
- 不新增未绑定核心用户任务的一级导航或大型能力域；
- 不在权威来源之外复制实现、成熟度或发布状态；
- 不以“AI 可以生成”为理由接受更多生产样板代码；
- 缺少范围批准的功能请求先回到 [PRD](../PRD.md)，而不是直接实现。

- [x] 创建六阶段路线图并启动阶段一；
- [x] 确认工作树和依赖参考处于可重复验证状态；
- [x] 重新运行后端 Release 构建与聚合测试；

## 第一批核心验证范围

本范围是简化工作的执行排序，不修改 [PRD](../PRD.md) 的目标范围，也不把代码存在提升为验证完成。选择现有成熟度台账中的三个 operator journey，并把共享身份与权限作为前置条件：

| 旅程 | 主要能力 | Owner | 当前 blocker 与证据 |
|---|---|---|---|
| J1 日常运维 | `CAP-01`、`CAP-02` 的控制台/日志子集、`CAP-05`、`CAP-06` | Operations / Administration | 以[成熟度台账](../test.md#能力成熟度唯一台账)和[已知缺口](../test.md#已知缺口)为准 |
| J2 玩家发现与处置 | `CAP-02`、`CAP-05` | Players / Administration | 以[成熟度台账](../test.md#能力成熟度唯一台账)和[已知缺口](../test.md#已知缺口)为准 |
| J3 备份、恢复与核对 | `CAP-03`、`CAP-05`、`CAP-06` | Operations / Administration | 以[成熟度台账](../test.md#能力成熟度唯一台账)和[已知缺口](../test.md#已知缺口)为准 |

执行顺序为 `CAP-05` 共享身份/权限前置条件，随后 J1、J2、J3。经济、奖励、Discord/GeoIP、社区玩法和世界工具继续作为扩展验证，不进入本轮核心收敛门槛。

第一轮只要求为上述旅程确认最小真实边界、失败语义、审计和回滚证据；实际 maturity 仍由[测试策略](../test.md)拥有。

## 第一批核心验证建议

下列内容只是阶段一的排序建议，不修改 PRD 范围或成熟度：

- 身份认证、角色和会话失效；
- 服务器状态与游戏就绪；
- 在线玩家和基础玩家处置；
- 控制台、日志和审计；
- 配置与 Mod 生命周期；
- 备份、恢复和回滚；
- 重启与基础计划任务。

最终选择必须引用 [PRD](../PRD.md) 的能力标识和[测试策略](../test.md)中的当前 blocker。

## 退出条件

只有同时满足以下条件才能进入阶段二：

1. 当前聚合构建、测试、OpenAPI、前端和复杂性检查已实际运行；
2. 失败、跳过、环境缺口和旧证据已在测试策略中诚实记录；
3. 第一批核心验证能力有明确 owner、边界和 blocker；
4. 三个追踪样本已选定；
5. 本阶段没有新增未说明的架构机制或事实源。

# 阶段二：复杂度盘点

## 目标

用真实变更路径判断哪些复杂性保护了风险，哪些只是转发、重复或未来假设。

## 工作项

- [x] 完成一个 C 级简单只读字段追踪；
- [x] 完成一个 B 级普通配置修改追踪；
- [x] 完成一个 A 级危险异步操作追踪；
- [x] 记录每个样本涉及的工程、文件、接口、DTO、映射、注册、测试和文档；
- [x] 标记每一层拥有的规则、边界、状态或失败语义；
- [x] 调查 `SIM-001` 至 `SIM-012` 初始候选；
- [x] 形成第一批不超过三个的已确认低风险候选；
- [x] 明确保留的本质复杂性，避免后续重复讨论。

## 评价问题

每个样本必须回答：

- 完成该任务必须理解哪些概念？
- 哪些概念来自真实业务或运行环境？
- 哪些层只传递相同参数或形状？
- 是否存在多个可独立变化的生产消费者？
- 删除一层会不会让 Application 依赖基础设施？
- 失败、权限、事务和恢复语义由谁拥有？
- 修改后如何证明行为没有退化？

## 退出条件

1. 三个样本都有完整证据；
2. 至少一个候选被证据判定为保留；
3. 第一轮实施候选不超过三个，且都有验证和回滚方式；
4. 没有把工程数、接口数或代码行数直接当作删除理由；
5. A 级边界没有在调查阶段被提前修改。

# 阶段三：删除偶然复杂性

## 目标

通过小批量变更验证简化方法能够真实缩短调用路径和理解成本，而不削弱安全、恢复或测试能力。

## 优先顺序

1. 重复文档事实和无效链接；
2. 无生产消费者的扩展点；
3. 纯转发且不跨边界的层；
4. 表达同一合同的重复 DTO 和映射；
5. C 级查询中过重的状态或审计机制；
6. 默认导航中未启用的扩展或实验能力；
7. 物理项目边界——只有前述低风险简化稳定后才调查实施。

## 每轮流程

```text
选择 1-3 个已确认候选
  -> 记录修改前路径和不变量
  -> 完成最小可回滚变更
  -> 运行聚焦验证
  -> 稳定后运行一次适用聚合验证
  -> 更新权威文档和候选结论
  -> 比较修改前后理解与变更成本
```

## 停止条件

出现以下任一情况时停止扩大本轮：

- 需要同时改变产品行为和物理项目边界；
- 不能说明如何回滚；
- 必须放宽状态真实性或授权才能减少层次；
- 聚焦验证无法覆盖受影响不变量；
- 减少文件后反而增加跨层依赖；
- 改善只体现在数字上，无法降低实际任务成本。

## 退出条件

1. 至少一轮候选已完成并通过适用验证；
2. 修改后的调用路径和概念数量有可解释改善；
3. A 级不变量和依赖方向没有退化；
4. 方法被证明可重复，或明确记录了不应继续的候选类型。

# 阶段四：收敛为三条标准路径

## 目标

让新功能和维护工作优先落入三条可识别路径，减少每个能力自行发明结构的情况。

## 工作项

- [x] 从已经稳定的真实切片提取简单查询 Golden Path；
- [x] 提取普通修改 Golden Path；
- [x] 提取危险异步操作 Golden Path；
- [x] 为每条路径记录适用条件、禁止事项和最小验证；
- [x] 将重复样板交给模板或生成器候选，而不是再抽象通用运行时；
- [x] 识别并解释确实无法落入三条路径的现有能力；
- [x] 更新简化章程中的生产锚点；

## 路径选择规则

- C 级查询默认选择简单查询；
- B 级修改默认选择普通修改；
- 只有存在持久异步、进程中断、不可逆副作用或结果核对时才选择危险异步操作；
- 路径可以省略没有责任的层，不能增加只为命名对称存在的层；
- 第四条路径必须由具体生产约束批准，不能由个人风格决定。

## 退出条件

1. 三条路径都来自生产代码而非纯目标设计；
2. 新开发者可从入口追踪到外部边界；
3. 每一层拥有明确责任；
4. 适用的静态检查或测试可以防止关键依赖倒退；
5. 系统架构与真实代码一致。

# 阶段五：自动化机械工作

## 目标

让 AI 和生成工具承担确定、重复、可校验的工作，而不是让生成速度推动生产代码膨胀。

## 候选范围

- OpenAPI 客户端和传输类型；
- Controller、migration 和 Feature 页面骨架；
- 权限测试矩阵；
- Adapter contract test 初稿；
- DTO/mapping 重复扫描；
- DI 注册和路由权限一致性检查；
- 文档链接和唯一事实源检查；
- 发布 manifest 和确定性配置。

## 自动化准入标准

自动化内容必须：

1. 由一个明确事实源决定；
2. 可以确定性重现；
3. 具有漂移检查；
4. 不隐藏业务不变量、授权或失败语义；
5. 生成失败时不会破坏现有生产内容；
6. 减少人工维护点，而不是批量创建更多必须阅读的层。

## 退出条件

1. 至少一个高频机械流程被安全自动化；
2. 人工事实源数量减少；
3. 生成物可复现且有漂移门禁；
4. 自动化没有改变产品或运行时语义；
5. 开发者仍能追踪生成结果对应的合同来源。

实际落实：`tests/docs/Test-SimplificationDocs.ps1` 以 UTF-8、PowerShell 5.1 兼容方式检查三份简化文档、相对本地链接、详细 `SIM-###` 标题唯一性、候选/样本状态、六阶段表格状态和三个生产 Golden Path 锚点；`tests/docs/tests/Test-SimplificationDocs.Tests.ps1` 覆盖通过、断链、重复候选和非法阶段状态。该检查器不解析产品成熟度，也不替代 `docs/test.md`。

# 阶段六：建立持续认知预算

## 目标

把简化从一次性重构转化为持续约束，关注任务理解成本，而不只是文件和接口数量。

## 建议指标

- 一个 C 级查询涉及的概念和手写层数；
- 一个 B 级修改需要同步的事实源数量；
- 一个 A 级操作从入口到终态的可追踪性；
- 新公共接口的生产理由；
- 新项目和跨项目引用的生产理由；
- 新页面对应的用户任务和现有导航位置；
- 新后台任务的 start、stop、drain、failure 和 recovery；
- 新持久状态的 migration、idempotency、rollback 和 restore；
- 新能力进入默认导航前的启用与验证状态；
- 新开发者完成标准任务所需时间。

## 门禁原则

- 指标用于发现趋势，不鼓励通过合并大文件、隐藏接口或减少测试作弊；
- 新抽象必须减少稳定重复、保护边界或服务多个生产消费者；
- 新状态必须说明现有状态为什么不能表达；
- 新文档必须说明其唯一职责和权威来源关系；
- 新 Feature 默认进入已有任务域，而不是增加一级导航；
- AI 生成代码与人工代码承担相同的审查和验证责任。

## 退出条件

1. 认知预算已进入贡献和评审流程；
2. 指标可以由脚本或小型人工检查稳定执行；
3. 指标不会奖励隐藏复杂性；
4. 新开发者任务有可重复的基线和改善证据；
5. 核心能力的验证进展优先于继续扩大功能表面积。

实际落实：`CONTRIBUTING.md` 的 Complexity and Cognitive-Budget Review Fields 现在要求风险等级、Golden Path、概念增减、事实源、AI 生成表面、生产接口理由、后台生命周期、迁移/恢复、导航任务和 verification/rollback。既有 `tests/complexity` 数值门禁继续负责可机器测量的项目、接口、导航、跨 Feature 和组合根趋势；`docs/test.md` 继续独占能力成熟度。

# 结构性决策门

以下变更只能在阶段二完成、至少一轮阶段三成功后单独批准：

- Domain 合入 Application；
- Hosting 合入 Bootstrap 或其他项目；
- 合并 Web、SevenDays、SQLite 或 Local Adapter 物理项目；
- 替换 Feature Module 机制；
- 大规模移动前端 Feature；
- 批量删除公共接口或测试；
- 改变认证、作业、恢复、审计或 OpenAPI 合同。

批准前必须说明：

- 要减少的具体概念和任务成本；
- 当前与目标依赖图；
- 不允许退化的不变量；
- 迁移顺序；
- 聚焦和聚合验证；
- 发布与真实边界影响；
- 可执行回滚方式。

# 完成定义

简化工作不是以“所有候选都处理完”为完成条件。满足以下结果时可以结束当前简化周期：

- 核心任务有清晰入口和标准路径；
- 低风险修改不再承担 A 级操作的全部机制成本；
- 高风险操作仍然可授权、可审计、可恢复且不谎报成功；
- 重复事实源和无生产价值抽象不再持续增长；
- AI 自动化减少机械维护点，没有扩大必须理解的生产表面积；
- 新开发者和核心用户的任务成本有实际改善；
- 后续复杂度可以由正常贡献流程持续控制，而不需要长期专项重构。
