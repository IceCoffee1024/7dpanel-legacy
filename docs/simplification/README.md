# 7DPanel 简化工作章程

## 目的

本目录用于推动 7DPanel 在不削弱安全边界、状态真实性和恢复能力的前提下，减少开发者和用户完成任务所需理解的概念数量。

本工作采用**原地、渐进、可回滚的简化**，不推倒重写，也不以减少文件、接口或项目数量本身作为成功标准。

## 文档职责

本目录不是新的产品、架构或测试事实来源：

- 产品目标、范围、`CAP-##`、`NFR-##` 和验收合同由 [产品需求文档](../PRD.md)拥有；
- 当前组件边界、运行时、依赖方向和部署设计由[系统架构](../architecture.md)拥有；
- 当前成熟度、证据、环境和发布门禁由[测试策略](../test.md)拥有；
- 页面信息架构、用户流程和交互状态由[界面设计](../design.md)拥有；
- 仓库工作流和复杂度审查字段由[贡献指南](../../CONTRIBUTING.md)拥有。

本目录只拥有三类辅助信息：

1. 简化工作的原则和决策边界；
2. 复杂度候选的调查证据与处置结论；
3. 简化工作的阶段、顺序和完成状态。

如果调查产生产品、架构或测试事实变化，必须更新对应权威文档；不得只在本目录宣布变化已发生。

## 当前决策

### 不推倒重来

当前系统已经识别并实现了游戏线程、外部 I/O、持久化、认证、审计、恢复和发布物等真实边界。重写会同时丢弃这些已知约束与已有证据，并不能消除 7DTD Mod 生命周期、Mono 进程、SQLite、异步副作用和跨平台发布等本质复杂性。

因此，简化工作的默认选择是：

- 保留本质复杂性；
- 删除偶然复杂性；
- 先缩短局部变更路径，再讨论物理项目合并；
- 每次只处理少量、有证据、可回滚的候选；
- 高风险能力的严谨性不能为了统一代码形态而退化。

### 停止继续扩张架构

在[路线图](roadmap.md)第一阶段退出前，非必要变更不得新增：

- 通用消息总线、插件系统、Repository 框架或状态机框架；
- 新的产品项目、基础层或通用生命周期抽象；
- 没有同一变更中生产消费者的接口、Registry 或未来基础设施；
- 重复的治理台账、实现状态或验证状态；
- 未绑定明确核心用户任务的新一级导航或大型功能域。

现有外部边界、跨项目依赖方向、第二个生产实现或消费者、稳定重复，以及已经批准的近期消费者，仍可构成抽象理由。测试便利本身不构成理由。

## 目标与非目标

### 目标

- 让新开发者可以沿一条清晰路径定位并修改一个业务切片；
- 让低风险查询和普通修改不承担危险异步操作的全部机制成本；
- 减少纯转发层、一对一无边界接口、重复 DTO、重复映射和重复事实源；
- 把核心能力的真实验证置于继续扩大实现表面积之前；
- 让用户按任务完成运维，不需要理解内部 Store、Job、Adapter 或状态机；
- 让 AI 自动生成机械工作，同时由开发者控制范围、不变量、失败语义和验收标准。

### 非目标

- 不以恢复旧项目目录、路由、认证、数据库或 UI 为目标；
- 不以单一文件、单一工程或最少接口为目标；
- 不取消游戏线程、认证授权、数据库迁移、审计、恢复或发布物边界；
- 不把当前固定能力扩展成任意脚本或通用插件平台；
- 不通过删除测试、放宽状态语义或隐藏失败来制造“更简单”的结果；
- 不在本目录重新定义产品范围或提升能力成熟度。

## 复杂性的分类

### 必须保留的本质复杂性

下列约束来自产品运行环境和副作用，不能通过重命名或合并项目消失：

- Unity/7DTD 可变对象只能通过受控游戏线程边界访问；
- HTTP 可用、Mod 已启动和游戏已就绪是不同状态；
- 队列接收、脚本启动和 HTTP 成功不等于最终副作用成功；
- SQLite migration、写入失败、进程中断和恢复必须有明确语义；
- SSE 可能断线、漏事件、重连和重放，不能替代权威持久状态；
- 备份、恢复、重启、经济、玩家和世界操作需要权限、审计和恢复策略；
- Windows/Linux、Mono、native SQLite 和发布程序集闭包需要候选 artifact 证据。

### 应优先调查的偶然复杂性

以下内容不是自动删除对象，而是进入[复杂度盘点](inventory.md)的候选：

- 不跨外部边界、只有一个实现和一个调用者、测试也不替换的一对一接口；
- 参数和返回值不变、没有规则、授权、事务或错误转换的纯转发层；
- 表达同一合同的重复 DTO、手写类型和映射；
- 在多个文档重复维护的实现、成熟度和门禁状态；
- 没有生产消费者的 Registry、扩展点和未来基础设施；
- 未启用或未验证却长期占据默认导航和主要学习路径的能力；
- 简单查询与危险异步操作使用几乎相同的调用层数和状态机制。

## 风险分级与设计强度

风险等级用于选择设计强度，不改变 [PRD](../PRD.md) 中的能力优先级。

### A 级：高风险或难恢复

典型能力包括备份恢复、世界修改、玩家物品与技能修改、经济扣款与发放、重启、身份与 API Key、配置与 Mod 文件修改、任意控制台命令。

默认要求：

- 明确 Application 用例和外部端口；
- 服务端授权和稳定身份；
- 幂等、并发或重复提交策略；
- 权威终态、`ResultUnknown` 或等价失败语义；
- 操作者审计；
- migration、恢复和回滚设计；
- 适用的真实边界与候选 artifact 证据。

### B 级：中等风险且通常可重试

典型能力包括公告、调度、聊天管理、踢出、访问名单和固定外部集成设置。

默认要求：

- 一个明确应用入口；
- 必要授权和最小审计；
- 可理解、可重试的失败结果；
- 只有跨越真实异步边界时才引入持久作业。

### C 级：只读、展示或容易恢复

典型能力包括概览、列表、历史查询、地图展示、日志筛选和 UI 偏好。

默认要求：

- 使用最短、可测试的读取路径；
- 保留来源、观察时间和未知值语义；
- 不进入 Job、持久状态机或通用审计，除非存在独立生产理由。

## 三条标准实现路径

新功能和重构应优先选择以下路径之一。需要第四条路径时，必须说明现有路径无法表达的真实约束。

### 简单查询

```text
Controller
  -> Read Port 或 Query Service
  -> Adapter
```

### 普通修改

```text
Controller 或固定游戏命令
  -> Application Use Case
  -> Store 或 Gateway
```

### 危险异步操作

```text
Controller 或固定游戏命令
  -> Application Use Case
  -> Persistent Job
  -> Bounded Worker
  -> External Boundary
  -> Audit / Reconciliation / Recovery
```

路径中的每一层都必须拥有规则、边界或状态转换；只传递相同参数的层应进入合并候选。

## 生产 Golden Path 锚点

以下不是新的架构层，而是从阶段二已追踪的生产切片中提炼出的默认走法。新变更应先判断自己属于哪条路径，再复用相同的责任分配；实际实现事实仍由[系统架构](../architecture.md)和[测试策略](../test.md)拥有。

| 路径 | 已验证生产锚点 | 每层必须负责 | 禁止的捷径 | 最小验证 |
|---|---|---|---|---|
| 简单查询 | `CAP-01`：`SevenDaysGameOverviewQuery` → `IGameOverviewQuery` → `GetOverviewUseCase` → `OverviewController` → OpenAPI 生成 `overviewGetQuery` → `overviewParser` → Admin 状态卡 | 游戏线程采样与就绪、应用聚合和 unknown/stale 语义、HTTP 合同、客户端信任边界 | Web 直接读取游戏对象；为单一读取再建 Job 或持久状态机；绕过 parser 使用生成 DTO 作为领域状态 | 适配器、Application、HTTP、parser、生成 query 的聚焦测试；适用时加 `api:check` |
| 普通修改 | `CAP-07`：`ColoredChatView` → `useColoredChat` → 生成 mutation → `ChatController` → `SaveColoredChatSettingsUseCase` → `IColoredChatStore` / `IChatRuntimeConfiguration` / `IChatOperationAuditTrail` | UI draft 和错误状态、Owner 授权、业务规范化、持久化后热应用、CAS snapshot、摘要审计 | Controller 直接写 SQLite；持久化失败仍更新 runtime；把客户端成功或 HTTP 202 当作最终副作用成功 | Store/用例顺序、HTTP/OpenAPI、runtime snapshot、Admin mutation 的聚焦测试 |
| 危险异步操作 | `CAP-03`：`RestoreConfirmModal` → `BackupsController` → `StageRestore` → Restore job/marker → `PendingRestoreApplier` → safety/rollback → startup migration/reconcile | 强确认、幂等和 CAS、marker/receipt、安全路径与 hash、终态和未知结果、启动恢复、审计/回滚 | 在线覆盖；让通用 worker 抢占 Restore；删除 safety copy 或把 Prepared 当成功；用一条布尔值替代终态 | 状态机、并发 claim、文件故障、回滚、启动三阶段、merge-once 和真实边界证据 |

### 路径选择规则

- C 级查询默认走简单查询；如果需要持久作业或危险副作用，必须说明具体生产约束。
- B 级修改默认走普通修改；只有跨进程、不可重试或需要持久恢复的动作才升级为危险异步操作。
- A 级操作默认走危险异步操作；不能因为当前实现同步返回就降低等级。
- 第四条路径必须同时写明：现有三条路径无法表达的生产约束、增加的概念、失败语义和回滚方式。
- 阶段二中发现的 `SIM-017` 说明“危险异步路径”内部仍必须按操作类型划分 claim 和状态转换；Golden Path 不授权所有 Job 共用一个 worker。

## 必须保留的架构边界

简化不得破坏以下约束：

1. Application 不引用 7DTD、SQLite、OWIN 或本地文件系统实现；
2. Web Controller 不直接访问 SQLite 或游戏活对象；
3. 游戏事件回调不等待 SQLite、网络或长时间后台工作；
4. 浏览器不能提交脚本路径、进程参数、环境变量或任意服务端执行描述；
5. 高风险操作不能把排队、启动或接收表述为最终成功；
6. gap、未知结果和部分失败不能被零值、缺失字段或乐观状态隐藏；
7. 认证、授权和审计在服务端执行，前端权限只用于可见性和体验；
8. 数据库升级、恢复和发布物仍须具备可验证、可回滚的流程；
9. OpenAPI 仍是 Web 与前端之间的唯一传输合同来源；
10. `7dtd-reference/` 仍是只读兼容性证据，不是产品源或发布内容。

## 产品与用户心智负担

代码简化不能替代产品收敛。简化工作使用“核心、扩展、实验”作为执行排序，不在此重新定义 PRD：

- **核心**：优先取得真实验证并形成默认任务路径；
- **扩展**：按需启用，不应占据所有用户的默认学习路径；
- **实验**：缺少真实边界证据时明确标识，不以代码存在宣称稳定。

用户界面应遵循：

- 按“查看服务器、处理玩家、安排重启、恢复备份、查询审计”等任务组织，而不是暴露内部模块名；
- 使用渐进式披露、安全默认值和常见预设；
- 未启用模块不占据默认导航；
- 根据角色隐藏不可达任务，但不以隐藏代替服务端授权；
- 把内部状态翻译为用户可行动的说明，同时保留不确定性；
- 高风险操作统一展示影响、可撤销性、备份、状态、操作者和恢复入口。

实际导航或交互变化必须更新[界面设计](../design.md)，并按[测试策略](../test.md)评估浏览器证据。

## AI 与开发者的职责

### 适合自动化或 AI 生成

- OpenAPI 客户端和传输类型；
- Controller、migration 和 Feature 页面骨架；
- 重复测试数据、权限矩阵和 Adapter contract test 初稿；
- DTO 映射候选、重复代码扫描和文档链接检查；
- 发布 manifest、机械配置和局部重构候选。

生成结果必须减少人工工作，不能因为生成便宜而扩大生产代码表面积。

### 必须由开发者负责

- 决定功能是否应该存在以及明确不支持什么；
- 定义业务不变量、信任边界和副作用范围；
- 设计队满、中断、重试、并发、部分提交和结果未知语义；
- 定义测试预言机、真实环境和发布验收标准；
- 判断新抽象是否减少系统级概念，而不只是减少局部重复；
- 审查 AI 生成代码的安全性、可恢复性和整体依赖影响；
- 对最终合入行为负责。

对于游戏线程、认证、migration、经济、备份恢复、世界操作、Harmony、并发队列和发布闭包，AI 只能生成候选实现，不能替代人工边界审查与真实验证。

## 成功指标

简化是否成功由行为和理解成本判断，而不是由代码数量单独判断：

1. 新开发者可以在半天内运行项目并定位一个业务切片；
2. 低风险小改动通常可以在一天内完成；
3. 一个业务切片可以通过有限的局部文件和一条标准路径理解；
4. A 级操作仍可授权、审计、恢复且不谎报成功；
5. 核心用户无需理解内部架构即可完成主要任务；
6. 核心能力的成熟度可以从 `Implemented` 推进到 `Verified` 和 `Release-ready`；
7. 新公共接口、项目、事实源和实现路径都有明确生产理由；
8. 简化后的变更具有针对性验证和明确回滚方式。

文件数、接口数和项目数只作为诊断信号。降低数字但增加跨层耦合、隐藏状态或削弱恢复能力，不算成功。
